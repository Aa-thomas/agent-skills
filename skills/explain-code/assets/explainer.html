Why a stale edit is rejected

A version check at the save boundary prevents an older edit from replacing a newer one.

The version travels with the edit

Imagine two editors opening version 4 of a record. Each sends an edit with expected_version = 4. Accepting both without checking the stored version could silently replace the first person's work.

  1. The first edit reaches the store. Its expected version matches version 4, so the store accepts the write and advances to version 5.
  2. The second edit arrives with version 4. Its conditional write no longer matches, so it cannot overwrite version 5.
  3. The application returns a conflict that lets the editor reload or reconcile the newer content.

The important boundary is the write itself. A check against an earlier loaded snapshot would leave room for another write between checking and saving.

UPDATE records
SET value = :value, version = version + 1
WHERE id = :id AND version = :expected_version;

-- No matched row means this write was not accepted.
-- The application must distinguish a missing record from a stale version.

Important alternatives

Illustrative analysis, not recorded author intent. A conditional write protects an earlier edit but makes conflicts visible to the user. That adds work to the interface and may require a reconciliation flow.

Last-write-wins is simpler when replacing an older value is an accepted product rule—for example, updating a disposable preference. It would be a poor fit when silently losing another person's edits breaks the editing contract. The actual product requirement should decide.

Reveal the reasoning without answering

The store must check the expected version as part of accepting the write. Checking only before the write leaves a gap where another edit can change the record. Rendering happens too late to protect it.
